# Investigation: Director Thread Operation Against Intended Workflow

## Summary
The inspected Director thread did create worker threads, but it repeatedly crossed the coordination/execution boundary: it duplicated worker checks inline, performed repo and production inspection, made production Supabase/Vercel changes, edited files, and narrated routine progress in the parent thread. The repo already documents the intended coordination-only, low-chatter, worker-owned model; the main gap is that the compact activation surface, worker launch acceptance, hooks, oracle/review triggers, recursive topic-thread orchestration, and cleanup lifecycle do not make that contract operationally hard enough under pressure. Any examples or incident playbooks added to the skill should be project-neutral, not Effervescenz-specific.

## Symptoms
- Parent thread `019e9220-e321-7bd1-b3ce-098140241a93` produced frequent user-facing progress chatter.
- Parent thread created workers but also duplicated or replaced their work inline.
- Worker threads appear to be normal Codex delegated threads, not explicit topic-level orchestrators or dynamic workflow packets with their own oracle/review/subagent lanes.
- No persistent oracle thread is visible in the inspected parent/spawned thread history.
- Finished worker sessions remained visible as separate created threads; no cleanup/archive lifecycle was apparent from the inspected transcript.

It edited repo files directly after receiving a normal implementation brief; it did not appear to act as a topic-level orchestrator, invoke a named dynamic workflow, create worker-internal subagents/threads, or own a worktree policy for its scope.
- In the parent thread, after starting workers for production verification, the Director said both workers were slow and ran the same non-mutating smoke/deployment probes inline. Later, during the production incident, it performed direct Supabase/Vercel tool calls and file edits inline, including a production schema hotfix and later a revert/repair pass.
- Prior memory for this repo says the intended Director contract is Codex-native, coordination-only, callback-first/low-chatter, with status/checkup/lookup answered from ledger state or delegated to worker threads. RepoPrompt should be optional context tooling, not the Director lifecycle adapter.

#### Root-cause conclusions
- **Primary root cause: model compliance failed at the coordination/execution boundary.** The docs already say the right thing in several places; the observed parent thread treated slow workers and urgent production state as permission to become an executor. The runtime adapter explicitly forbids that and says to report a blocker when no real worker can own execution (`plugins/codex-director/skills/codex-director/references/runtime-adapters.md:20`, `plugins/codex-director/skills/codex-director/references/runtime-adapters.md:49-50`).
- **Secondary root cause: enforcement is soft.** Hooks are intentionally non-blocking reminders (`plugins/codex-director/hooks/README.md:28-33`) and the hook text is short (`plugins/codex-director/hooks/director-hook.py:23-41`). Nothing in the implementation prevents inline repo/prod tool use, forces `.workflow/` creation, rejects missing activation reports, creates review/oracle lanes, or archives completed workers.
- **Tertiary root cause: the strongest operational details are in long references.** The compact skill has the core rules, but the most operational no-inline adapter language, ledger schema, dynamic-workflow triggers, and archive/cancel semantics live in references (`plugins/codex-director/skills/codex-director/references/runtime-adapters.md:16-34`, `plugins/codex-director/skills/codex-director/REFERENCE.md:145-184`, `plugins/codex-director/skills/codex-director/references/dynamic-workflow-integration.md:31-43`). Under time pressure, the Director likely followed the broad "help solve the production issue" intent rather than reloading/applying the long adapter contract.
- **Quaternary root cause: public/default prompts leave borderline cases underspecified.** README and manifest promise coordination and workers, but default prompts do not explicitly warn: do not inspect repos, run smoke probes, query production, edit files, or mutate external systems inline (`README.md:47-51`, `plugins/codex-director/.codex-plugin/plugin.json:36-39`). That matters because the observed failures were borderline "checking/remediation" actions the model may classify as coordination.

#### Skill-improvement recommendations
- **Add a compact pre-tool classification checklist to `SKILL.md`:** ledger/conversation coordination is allowed inline; repo/docs/code/prod inspection is worker-only; implementation/edit/test/deploy/external writes are worker-only; if no worker adapter is available, report a runtime blocker. Include explicit examples: production smoke tests, Vercel/Supabase/Sentry inspection, env/token probing, schema hotfixes, deployment probes, test runs, file edits, and rollback/repair passes.
- **Make production/external-write work mandatory dynamic workflow unless explicitly excepted.** For production incidents, require `.workflow/<slug>/` with safety/rollback gates, read-only verifier packet, remediation packet, independent review/oracle, verification packet, final report, and worker archive/cleanup. The current trigger rules already support this (`plugins/codex-director/skills/codex-director/references/dynamic-workflow-integration.md:31-43`); promote the production incident subset into the compact skill.
- **Strengthen the worker brief and activation acceptance policy.** Treat missing activation report, missing research/plan review rationale, or missing adversarial review/oracle policy as incomplete launch. Recommended lifecycle: steer once for activation; if still missing, mark stale/cancel_requested and re-brief/relaunch; do not accept completion without required evidence and review.
- **Make oracle/review mandatory triggers explicit.** Required review/oracle lane before completion for production config/data changes, schema/database changes, auth/security/secrets, deploy/rollback/remediation, conflicting worker evidence, indirect verification, or cross-module implementation. If unavailable, the Director should record residual risk and ask the user before accepting completion.
- **Make the visible update gate an executable pre-send rule.** Add one sentence to compact skill/default setup/hook output: "Before any user-visible message, verify it is final evidence, a real blocker/decision, safety/production authority, ownership handoff, or stale/cancel/archive state; otherwise write only to ledger." This targets the exact chatter observed.
- **Improve hooks while preserving advisory intent.** Sharpen `UserPromptSubmit` to say: "If this requires repo/docs/code/prod inspection, create/continue a worker; do not inspect inline; do not narrate polling/checking/rerunning." Sharpen `Stop` to require evidence captured, active/stale/cancelled workers accounted for, and archive decisions recorded. Hooks remain advisory, but the reminder should name the observed failure modes.
- **Clarify manifest/default prompts and README examples.** Add no-inline language to default prompts/setup examples so first activation carries the boundary, not only the long references. Consider explaining that plugin `Read`/`Write` capability belongs to worker-owned workflows and plugin installation, while the Director thread itself remains coordination-only.
- **Add an incident-mode example.** A production incident example should show the desired lifecycle: ledger check, read-only verifier worker, user authority gate, remediation worker, oracle/review lane, verification worker, evidence reconciliation, archive/cleanup, concise final status. That would make the intended behavior concrete for the exact scenario observed.

## Root Cause

### Observed contract violations
The parent Director thread violated the documented coordination-only contract by performing project work inline. It created worker threads, but then duplicated or replaced them with parent-thread execution, including production smoke/deployment probes, Supabase/Vercel remediation, production schema hotfix/revert work, repo file edits, and live status/checkup work requiring repo/prod inspection.

The parent also violated the visible update gate by producing frequent process narration for checking, polling, rerunning, narrowing, and progress updates that should have stayed in the Director ledger.

The spawned workers were real worker threads, but the observed implementation lane appeared under-packetized: no clear dynamic workflow artifacts, no visible persistent oracle/review lane, incomplete evidence of activation/report gating, no topic-thread-as-orchestrator behavior, and no apparent archive/cleanup lifecycle after completion.

### Documentation and enforcement gaps
The intended behavior is well documented, but enforcement is soft. The strongest no-inline inspection/execution language is spread across long reference files, while the compact activation surface still allows the model to rationalize live checks or urgent remediation as coordination. Hooks are explicitly advisory and do not block inline repo/prod tool use, force worker creation, require dynamic workflow artifacts, enforce low chatter, validate activation reports, create review/oracle lanes, or archive completed workers. Default prompts and marketplace metadata describe coordination and worker use, but do not strongly restate that the Director thread itself must not inspect repos, run smoke probes, query production, edit files, or mutate external systems. They also do not make the recursive model concrete enough: each distinct topic may need a top-level topic thread that coordinates its own worktree, subagents/child threads, workflow packets, oracle/review lanes, and cleanup lifecycle rather than behaving as a leaf implementer.

Net root cause: model compliance failed at the coordination/execution boundary, and the plugin's current prompts/hooks/templates did not make that boundary operationally hard enough under urgent production pressure.

## Recommendations
1. Promote a hard no-inline-project-work checklist into the compact skill/default activation surface. Before any Director action, classify it as ledger/conversation coordination, worker-only repo/docs/code/prod inspection, worker-only implementation/test/deploy/external write, or runtime blocker. Explicitly name smoke tests, deployment probes, Vercel/Supabase/Sentry checks, env/token probing, schema hotfixes, test runs, repo edits, and rollback/repair as worker-owned.
2. Make the examples and playbooks generic. Replace project-specific examples with neutral scenarios such as production incident, schema migration, preview environment rollout, multi-repo release, security review, or data import. Effervescenz can remain only as a regression case in this investigation report, not as the skill's canonical example domain.
3. Make topic threads recursive orchestrators by default for non-trivial topics. A created topic thread should own the topic scope, decide whether it needs a worktree, create/coordinate worker-internal subagents or child threads, maintain its own topic ledger/workflow packet state, request oracle/review lanes, and return concise evidence to the parent Director. Leaf implementation should be delegated below that topic thread unless the topic is explicitly small enough for a single worker.
4. Make production/external-write tasks mandatory dynamic workflow unless explicitly excepted. Production incidents should require durable task state, approval/safety gates, read-only verification, remediation worker ownership, independent review/oracle, final verification, evidence capture, and archive/cleanup.
5. Define mandatory oracle/review triggers before completion for production config/data changes, schema/database work, auth/security/secrets, deploy/rollback/remediation, conflicting worker evidence, cross-module implementation, and indirect or incomplete verification.
6. Strengthen worker launch and activation acceptance. Treat missing activation reports, missing review/oracle policy, missing research/plan rationale, missing topic-orchestrator/worktree policy, or missing evidence format as incomplete launch. Steer once; if still noncompliant, mark stale/cancelled, archive after evidence capture, and relaunch with a clean brief.
7. Make the visible update gate an executable pre-send rule. Every user-visible Director message should match one allowed category: final evidence, real blocker/decision, safety/production/destructive approval, ownership handoff, or stale/cancel/archive state. Everything else stays in the ledger.
8. Make archive/cleanup a completion criterion across both parent and topic threads. A task should not be considered fully reconciled until parent-level and topic-level worker evidence is captured, completed threads are archived or blocked with reason, stale threads are cancelled/archived, and cleanup/reconciliation work is assigned below the right orchestrator.
9. Clarify public/default prompts and metadata so first activation carries the boundary: the Director coordinates only and must not inspect, test, edit, deploy, or query production inline; non-trivial created threads coordinate their topic rather than doing all work directly.
10. Add generic incident-mode and multi-topic examples showing the correct flow: ledger check, topic thread creation, topic-owned worktree decision, verifier/research subagents, user authority gate, remediation/build worker, oracle/review lane, verification worker, evidence reconciliation, archive/cleanup, concise final status.

## Preventive Measures
- Require a Director self-check before tool use: is the next action coordination-only or project work? If project work, dispatch/continue a worker or report a worker-runtime blocker.
- Add a closeout checklist that accounts for active, completed, stale, cancelled, archived, cleanup-required, and review/oracle-required workers.
- Do not accept worker output without activation, topic-orchestrator policy, worktree decision, done-criteria evidence, verification summary, review/oracle status, and residual-risk statement.
- For every non-trivial request, explicitly record why `.workflow/` is used or why it is not needed, and whether the created topic thread is allowed to act as a leaf worker or must orchestrate subagents/child threads.
- Use this observed thread as a low-chatter/coordination regression scenario: parent must not narrate polling, perform prod probes inline, mutate production inline, or leave completed workers unarchived.
- Keep hooks advisory, but sharpen reminders to name the known failure modes: no inline repo/prod inspection, no polling narration, capture evidence, and account for stale/cancel/archive.
- Keep the full references, but ensure compact `SKILL.md`, README examples, default prompts, and worker brief templates all repeat the non-negotiable boundary.
